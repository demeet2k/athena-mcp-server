## Automatic validation, manual publication

V3.4 separates **validation cadence** from **publication authority**.

Every push to `master` automatically executes the same release-quality chain used on pull requests: syntax, full unit corpus, critical invariants, hardened stdio smoke, host-bound `PROMOTION.2` qualification, wheel build, clean installation outside the repository, immutable release-candidate attestation/checksums, and candidate artifact upload. There is intentionally no path filter on the master-push trigger: even a sibling operational or evidence-only commit changes the exact repository head and therefore receives a fresh V3.4 validation coordinate.

For non-PR validation, package-readiness additionally fetches `origin/master` and requires:

`RELEASE_HEAD == origin/master`.

If master has advanced while an older validation run is still executing, that older run cannot produce a current package-readiness receipt.

Publication authority is unchanged: the `publish` job still executes **only** when `github.event_name == 'workflow_dispatch'` on `refs/heads/master`.

`AUTOMATIC_VALIDATION != AUTOMATIC_PUBLICATION`.

`EVERY_MASTER_HEAD_VALIDATED != EVERY_MASTER_HEAD_PUBLISHED`.

`MASTER_PUSH_PACKAGE_READY != RELEASE_PUBLISHED`.

`STALE_MASTER_VALIDATION != CURRENT_RELEASE_CANDIDATE`.

A master-push release attestation records the validation event and `publication_performed=false`; it is evidence for exact-head package readiness, not evidence that a tag or GitHub release was created.
