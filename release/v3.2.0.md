## Trusted promotion boundary

PROMOTION.2 distinguishes caller-bound readiness from trusted external qualification.

`athena_promotion_evaluate` can bind exact-head caller CI/smoke packets but can only reach `ATTESTED_READY` without an internal trusted verifier receipt.

`GITHUB_PROMOTION_VERIFIER.1` independently fetches host-configured GitHub check-runs and requires one coherent exact-head Actions run/check-suite containing successful `syntax`, `unit`, `critical-invariants`, and `smoke` checks. It never splices checks across runs/suites and the caller cannot select repository/API/run/trusted-app/check roots.

The release workflow itself repeats the five-stage qualification chain on the exact release commit:

`syntax ∧ unit ∧ critical-invariants ∧ smoke → promotion-qualification`.

The trusted PROMRUN receipt produced by that release workflow is copied into the immutable release assets and bound into `release-attestation.json` before publication.

Publication is allowed only from an explicit release workflow dispatch on `master`. 1. base `athena://manifest == ATHENA.RUNTIME.UNIFIED.9`;
2. effective `athena_runtime_manifest == ATHENA.RUNTIME.UNIFIED.10`;
3. `athena://architecture/inventory == ATHENA.ORGAN.INVENTORY.1.1`;
4. `athena://architecture/drift` reports PASS for the declared coordination cohort;
5. V13 robust tools/resources and Message Board/Cohesion/Party V3.2 public surfaces are present;
6. the trusted PROMRUN receipt binds the exact release head.

It then performs exact-head tag compare-and-swap before creating/updating the GitHub Release.

If master moves, qualification and publication must be rerun for the new exact head.
