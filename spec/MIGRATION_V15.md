# MIGRATION TO V15 / 3.4.0 / UNIFIED.11

## Source ancestry

V15 did not branch from the old V14 canonical head. It began from live `master` after the V14 promotion and first inherited the operational-basis Message Board/Party/Cohesion ontology hardening. While Ω15 was in flight, `master` advanced again with Deployment.2.

The correct migration rule is therefore:

`NEW_SUCCESSOR != REPLAY_OLD_BASE`.

A true two-parent Git braid is required when live organism state advances on an overlapping integration surface.

## Release lineage

V3.3 distribution evidence remains frozen as evidence for V3.3 bytes. V3.4 receives a distinct release manifest/notes/workflow. The live V3.3 publisher is retired from the V3.4 tree after the new V3.4 workflow exists.

`OLD_RELEASE_RECEIPT != NEW_RELEASE_EVIDENCE`.

## Trust migration

The trusted verifier is not version-bumped merely because the Collective frontier advances. Its trust law remains host-bound and exact-head scoped. A branch receipt does not qualify the later merge SHA.

## Deployment migration

Deployment.2 is inherited without conversion into a Collective layer. V15 must retain deployment tools/resources/operational-basis classification and all Deployment.2 tests.

`COLLECTIVE_CALIBRATED != DEPLOYMENT_AUTHORITY`.

## Failure policy

If a V15 release chart, manifest chart or protocol chart remains V14/3.3/UNIFIED.10, repair the migration coordinate rather than weakening tests. If a scientific estimator fails, repair the implementation rather than widening claim language. If live master moves again, braid again before merge.
